   A: Absolutely — your updated demo is excellent, and now we can clearly **see the difference** caused by how the regex is applied in context.

   Let’s go step-by-step:

   ---

   ## 🔎 The Input:

   Your text includes a line like:

   ```plaintext
   happy!
   
   <|endoftext|>
   Once upon a time,
   ```

   With actual newline characters (`\n`), not string literals like `"\\n"`.

   ---

   ## 🔍 Your Regex Logic

   ### 1. `pattern_with_specials`

   ```python
   pattern_with_specials = f"(?:{special_token_escaped})|{PAT}"
   ```

   This is run **directly on the full text** using `re.finditer(...)`.

   So the regex is applied **across the entire string, including the special token**.

   ### 2. `pattern_without_specials`

   This one splits the text manually:

   ```python
   text_split = text.split("<|endoftext|>")
   ```

   Then applies `re.finditer(PAT, ...)` separately to each chunk, avoiding interference from the special token.

   ---

   ## ✅ Observed Outputs

   ### 🔹 **Pattern WITH special tokens**

   ```python
   ['Lucy', ' was', ..., '!', ' \n', '\n', '<|endoftext|>', '\n', 'Once', ' upon', ...]
   ```

   > Whitespace is split into two tokens: `' \n'` and `'\n'` (instead of `' \n\n'`)

   ### 🔸 **Pattern WITHOUT special tokens**

   ```python
   ['Lucy', ' was', ..., '!', ' \n\n']
   ['\n', 'Once', ' upon', ...]
   ```

   > The `' \n\n'` is preserved as **one token**, exactly what you'd expect from a greedy `\s+`.

   ---

   ## 🧠 Why the Difference?

   Here’s the core reason:

   > **Putting the special token match `(?:<\|endoftext\|>)` in front of the regex changes how the regex engine chooses matches**.

   In this case:

   * The regex engine hits a point where it sees: `' \n\n<|endoftext|>'`
   * Since `<|endoftext|>` is a **valid match** by itself, the regex tries to **greedily match everything it can before that**, but without combining it all.
   * So it sees:

   * `' \n'` — matched as one `\s+`
   * `'\n'` — matched as the next `\s+`
   * Then `<|endoftext|>` — matched by the special token clause

   This is **different** than when the text has already been split on `<|endoftext|>` — in that case, the chunk being scanned **ends** before `<|endoftext|>`, so the regex has **no incentive to break things up** and instead just matches `' \n\n'` as a whole.

   ---

   ## 🧪 Summary Table

   | Situation                  | Regex Input               | Matched Tokens | Why                                                             |                      |           |     |                                                                |
   | -------------------------- | ------------------------- | -------------- | --------------------------------------------------------------- | -------------------- | --------- | --- | -------------------------------------------------------------- |
   | **With special tokens**    | Entire text including \`< | endoftext      | >\`                                                             | `' \n'`, `'\n'`, \`< | endoftext | >\` | Engine splits whitespace to greedily isolate the special token |
   | **Without special tokens** | Text split before token   | `' \n\n'`      | Engine sees all whitespace as one unit, nothing breaks it apart |                      |           |     |                                                                |

   ---

   ## ✅ So What Should You Do?

   If your goal is to **preserve merged whitespace tokens like `' \n\n'`**, the best approach is:

   ### ✅ **Split on special tokens first**, then tokenize each chunk with the original pattern:

   ```python 
   chunks = re.split(f"({special_token_pattern})", text)
   for chunk in chunks:
      if chunk in special_tokens:
         yield chunk
      else:
         for match in re.finditer(PAT, chunk):
               yield match.group(0)
   ```

   This ensures:

   * Special tokens are matched exactly and separately
   * Whitespace runs like `' \n\n'` are preserved as full tokens
   * Regex greediness is **uninterrupted by disjunctions**

# 8.3
优化点
 - 在merge 一个pair（2个token），变为1个token的时候。
   - 对于这2个pair，当前有它们的频率。
   - 那么合并后，是否有什么捷径可以呢？例如可以某个频率表里，将这2个token的频率合并，并增加一个新单词呢？我们并不能简单地想到一个这样的方法。但是，我们可以从naive的实现出发，寻找优化点。
      
   举个例子，给出一段文本，pretokenization中统计出，有"word"（出现2次）和"cork"（出现3次）。
   根据pdf P8，重走一遍merge的流程：

   还未merge之前，首先统计出这些pair的频率:
      首先统计单词频率：`{"w o r d": 2, "c o r k": 3}`，
      word中有wo, or, rd 3个pair，每个出现2次。cork中有co, or, rk 3个pair，每个出现3次。
      合计为`{ "o r": 5, "c o": 3, "r k": 3, "w o": 2, "r d": 2}`
   
   合并出现次数最多的"o" 和 "r"：
      首先统计单词频率：`{"w or d": 2, "c or k": 3}`，
      word中有w or, or d 2个pair，每个出现2次。cork中有c or, or k 3个pair，每个出现3次。
      合计为`{ "c or": 3, "or k": 3, "w or": 2, "or d": 2}`.

   为了更改一个pair，我们需要：
   1. **查找所有**相关的单词，以及它们的频率。
   2. 对于其中的每个单词，**查找所有**包含pair的地方，并将原本的2个token替换为1个。"w o r d" -> "w or d", "d e c o r a t o r" -> "d e c or a t or"
   3. 重新统计pair的频率。

   这些“查找所有”，都是线性时间到常数时间的可观的优化点。

   第一步不难优化，原本在所有的单词中查找，实际上只需要维护 pair -> 单词 的映射，并及时更新即可。

   第二步和第三步的优化需要依赖于以下的观察。

   我们发现，这2个map中，`"c o": 3, "r k": 3`和`"c or": 3, "or k": 3`非常接近，`"w o": 2, "r d": 2`和`"w or": 2, "or d": 2`也非常接近。

   PDF P8 - Optimizing the merging step中也提到，"The naïve implementation of BPE training in the stylized example above is slow because for every merge, it iterates over all byte pairs to identify the most frequent pair. However, the only **pair counts** that change after each merge are those that overlap with the merged pair."

   也就是说，这次操作实际上对于pair的频率表，只造成了比较小的影响。但是作业PDF结论实际上不直观：词频的变化是通过单词的变化统计出来的，我们需要先考虑合并对单词的影响。

   我们在操作一个单词的时候，例如word，我们想merge其中的一个pair，需要将这个pair左侧和右侧pair的对应token替换为"or": "w o r d" -> "w or d"（在pair->word中记录位置信息，也可以将第二步优化为常数时间。[思路](#思路)），即将单词的频率表中的`"w o r d": 2`，替换为`"w or d": 2`。
            
   也就是说，merge "o r"这个pair的时候，操作word这个词，即将单词的频率表中的`"w o r d": 2`，替换为`"w or d": 2`, 会对pair的频率表进行如下影响：
   - 原本"w o"这个pair，每当"w o r d"出现，它就会出现，现在这个词被移除了，加入的新词"w or d"中也没有"w o"这个pair。这个操作，对于"w o"这个pair的出现次数，会使其减少"w o r d"这个词的词频 - 2。
   - 增加了一个新词"w or d"，词频为2，这个操作，对于"w or"这个pair的出现次数的影响是，会使其增加"w or d"这个词的词频 - 2。如果之前没有出现过"w or"这个pair，就将其加入频率表。

   对于"r d"这个pair的频率，也进行类似的更新：
   - 原本"r d"这个pair，每当"w o r d"出现，它就会出现，现在这个词被移除了，加入的新词"w or d"中也没有"r d"这个pair。这个操作，对于"r d"这个pair的出现次数，会使其减少"w o r d"这个词的词频 - 2。
   - 增加了一个新词"w or d"，词频为2，这个操作对于"or d"这个pair的频率的影响是，会使其增加"w or d"这个词的词频 - 2。如果之前没有出现过"w or"这个pair，就将其加入频率表。
   
   因此，pair的频率表中，只需要更新"those that overlap with the merged pair"。实际上就是说被merge的pair左右两个pair.

   我们还可以通过一个例子说明合并操作为什么不会造成其它的影响。可以观察，如果把word这个词替换成例如swordfish之类的词，可以发现作出这个替换操作后，pair频率表发生的变化，依然只有"w o" 和 "r d"的频率和，不相邻的那些pair的频率，例如位于开头的"s w"，实际上并不会发生变化。

   还未merge之前，首先统计出这些pair的频率:
      首先统计单词频率：`{"s w o r d f i s h": 2, "c o r k": 3}`，
      swordfish中有wo, or, rd 3个pair，每个出现2次。cork中有co, or, rk 3个pair，每个出现3次。
      合计为`{ "o r": 5, "c o": 3, "r k": 3, "s w": 2, "w o": 2, "r d": 2, "d f": 2, "f i": 2, "i s": 2, "s h": 2}.`
   
   合并出现次数最多的"o" 和 "r"：
      首先统计单词频率：`{"s w or d f i s h": 2, "c or k": 3}`，
      word中有w or, or d 2个pair，每个出现2次。cork中有c or, or k 3个pair，每个出现3次。
      合计为`{ "c or": 3, "or k": 3, "s w": 2, "w or": 2, "or d": 2, "d f": 2, "f i": 2, "i s": 2, "s h": 2}.`.

原版的 Position Encoding 是一种对“绝对位置”的建模。它作用于 embedding 层，直接加在词向量上。在这一层，模型的语义信息还没有开始做交互，无法引入“相对位置”信息。因此，后续的衍生版本将 Position Encoding 移动到了 self-attention 的  中（这里也是唯一能够获取到“相对位置”的地方）。这样一来，Position Encoding 从原本的“只在embedding 层计算一次”，变为“每个 attention 层计算一次”。
